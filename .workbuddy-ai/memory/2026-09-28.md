## CodeGate — Phase 0 架构设计（完成）

**项目**：CodeGate，开源 Remote PTY Gateway。浏览器安全访问本机原生 CLI（Claude Code / Codex / PowerShell / Bash 等）。
三组件：Server（Go，Control Plane + Relay）、Agent（Go，本机执行边界，只出站 WSS）、Web（Vue 3 + xterm.js）。
硬性边界：不做 Shell、不做 Terminal Emulator、不解析 CLI 业务、不修改输出、不做 AI Agent。

**产出**：`docs/PHASE0-ARCHITECTURE.md`（19 个章节 + 3 个附录）

### 关键决策（已写入文档 §0.1，共 20 条）
- **D6 Windows PTY**：用 `aymanbagabas/go-pty` 封装 ConPTY，外面套自研 `terminal.Terminal` 接口（保留替换逃生通道）。不手写 `CreatePseudoConsole`。
- **D10 控制面划分**：REST 只管 auth / device / ws-ticket / health；**session 全生命周期走 client WebSocket**。理由：Agent 是最终执行者，`session.exit` 事件只能从 WS 来，走 REST 会形成双写状态分歧。
- **D3 数据库**：SQLite + `modernc.org/sqlite`（纯 Go 无 cgo）起步，后期换 PG。手写 SQL + 单一 `storage.Store` 接口，不引 ORM。
- **D12 Agent 鉴权**：Ed25519 挑战-应答（nonce 单次 + 30s TTL 防重放），非长期 bearer token。
- **D11 浏览器 WS 鉴权**：`POST /ws-ticket` 换一次性 ticket，避免 JWT 进 URL。
- **D15 多客户端**：MVP 单 attach，新连接顶掉旧连接（resize 语义在多客户端下无解）。
- **D14 二进制帧**：20 字节头（Version 1B / Type 1B / Flags 2B / SessionID 16B）+ 裸 payload。**建议删掉规范里的 `PayloadLength`**——WS 帧自带长度，冗余字段是多余攻击面。
- **D17**：MVP 不用 xterm WebGLAddon（浏览器 WebGL context 上限 ~16，SPA 反复挂载会 context lost）。

### 对规范的 4 处修改建议
1. **Session 状态模型**：内部拆成正交两轴 `ProcState × AttachState`，对外仍派生回规范要求的 6 个扁平值。原因：`running`（进程活着）和 `detached`（有人看着）不是同一维度，并列会导致状态机不自洽。
2. **`Wait()` 返回 `ExitResult` 而非 `error`**：必须区分"正常退出但 exit code=1"和"PTY 故障"。
3. **删掉 `pkg/` 目录**；前端源码放仓根 `web/`，构建产物 embed 到 `internal/server/webui/`（`go:embed` 只能 embed 包目录之下的文件，且 `node_modules` 不能进 module）。
4. **`internal/session/repository.go` 移到 `internal/storage/`**：Agent 侧没有 DB，放在 session 包会让 Agent 二进制 import 数据库代码。

### 识别出的最高风险
- **R1（最高）ConPTY 不是透明字节管道**——它内部维护屏幕缓冲区并重绘，可能改写/合并序列，影响全屏 TUI（Claude Code、vim、htop）。**Phase 2 PoC 是准入门槛，不通过就停下重新评估，不能硬往下做。**
- **R2** Attach 重放保真度：buffer 尾部可能切在转义序列中间。缓解 = 清屏 + 对齐安全边界 + 文档说明是 best-effort。
- **R3** 慢消费者拖死 Agent（PTY 写满 → CLI 阻塞）。缓解 = PTY 读循环永不阻塞，ring buffer 永远写，实时流走有界 channel 满了就丢并标记 DROPPED。
- **R5** Agent 重启必然丢 Session（PTY 句柄随进程消失，无可靠跨进程继承方案）。**必须在 UI 和文档里说清楚**，并用 Job Object（Windows）/ 进程组（Unix）保证不泄漏孤儿 conhost。
- **R6** 中继内存：粗算 1000 条 Agent 连接 ≈ 1 GB（send channel 是主要开销）。需 P4 实测，目标 < 100 KB/空闲连接。

## R1 实测完成 —— 风险解除（详见 docs/PHASE0-R1-CONPTY-FINDINGS.md）

**方法**：本机没 Go，改用 **Python ctypes 直接调 ConPTY**（`tools/conpty_probe.py`），配 `tools/ansi_report.py`（模式时间线 + 能力查询 + 自写 VT 解析器还原屏幕）。好处是拿到的字节流与未来 Go 实现完全同源。

**结论：ConPTY 能正确承载这些 TUI。** Codex（ratatui）和 OpenCode（opentui）的全屏 TUI 都被逐字还原，box-drawing/宽字符/emoji 全对。resize 实测生效（100x30 → 60x20）。

**但挖出 3 个必须处理的坑：**

1. 🔴 **父进程 std 句柄会被子进程继承，输出绕开伪控制台。** 父进程 stdout 一旦重定向（管道/服务环境），子进程 stdout 跟着走，ConPTY 只吐自己的初始化序列（16 字节）。**Agent 作为 Windows Service 运行时必然踩到。** 修复：`CreateProcessW` 前后把父进程三个 std 句柄临时置 NULL（实测有效：子进程 stdout 立刻变成 `BUF=100x30`）。
2. 🔴 **不设 `TERM`，Codex 直接拒绝进 TUI**（`TERM=dumb` → 411 字节 + `Continue anyway? [y/N]`；设 `xterm-256color` 后 → 3,976 字节完整 TUI）。Agent 必须白名单构造子进程环境（强制 `TERM`/`COLORTERM`/`LINES`/`COLUMNS`），**不能整体继承**——本机坏掉的 `https_proxy` 也会被一起传下去（Claude Code 报 502 就是证据）。
3. 🟠 **备用屏幕与模式状态在 attach 时丢失** → 新增 **`ModeTracker`** 组件（§7.7）。三个 CLI 的模式设置全在启动头 300 字节内（`?1049h` 等），ring buffer 早就覆盖掉了。attach 必须走 6 步：清屏 → 重放模式前导 → 清屏 → 重放 buffer → **无条件补 `?2026l`** → 实时流。最后这步解决「同步输出未配对导致终端画面冻死」——低概率但只在重连路径复现。

**其他实测发现：**
- **`0x03` 不产生 `CTRL_C_EVENT`**：子进程收到的是字符（`ORD=3`），不是信号。对 raw mode TUI 恰好正确（应用自己解释），对 shell 待 Phase 2 确认。
- **目标 CLI 会主动查询终端能力并在等回答**：OpenCode 发了 `CSI > 0 q`(XTVERSION)、`CSI ? u`(Kitty 键盘)、`OSC 4;0;?`(调色板)、`CSI 14 t`(像素尺寸)、`OSC 1337;Capabilities`。CodeGate 是透明中继，这些必须由 **xterm.js** 回答 → Phase 6 要逐条实测，有缺口就在前端加一层极薄的「终端能力应答层」（`registerCsiHandler`），**不在 Server/Agent 里做**。
- **渲染栈**：Claude Code = Bun 编译的单文件（自有渲染层，`react-reconciler` 零命中，存疑）；Codex = Rust **ratatui + crossterm**；OpenCode = Bun + **opentui**（Zig 核心）。
- ⚠️ **踩坑记录**：用 `ink` 当框架特征完全不可靠（是 `link`/`thinking` 的子串，误报 8752 次）。必须用无歧义标记（`react-reconciler`/`yoga-layout`/`@opentui`）。
- Claude Code 用 `\x1b[1C`（CUF）代替空格排版 → 再次证明任何对字节流的"整理"都会破坏布局。

### ★ 新坑：Go SDK 用 python 解压 → 整个标准库变密文

```
src/sync/atomic/asm.s:1:1: invalid UTF-8 encoding
src/sync/atomic/asm.s:1: expected identifier, found "\u0a11"
```

`\u0a11` 就是亿赛通密文的特征串（和 skill `esafenet-dlp-dev-env` 里记的 esbuild 报错同源）。

**根因**：skill 里那条「读要白名单，写要非白名单」——**python 在白名单里，所以它解压出来的文件被驱动加密了**；而 `asm.exe`/`compile.exe`/`go.exe` 都不在白名单，读到的是密文。密文 = 明文 + 4096 字节（实测 7168 vs 3072）。

**修法（已验证）**：用 **Windows 自带的 `C:/Windows/System32/tar.exe`** 解压。它不在白名单，落盘即明文。
```bash
C:/Windows/System32/tar.exe -xf go1.27.1.windows-amd64.zip -C <目标目录>
```
于是有 `1.27.1/`（python 解压，密文，废弃）和 `1.27.1-plain/`（tar 解压，可用）两份，**GOROOT 必须指向 `-plain` 那份**。

> **可推广的结论**：以后在这台机器上装任何**带源码的工具链/SDK**（Node 源码包、Python 源码、各种 SDK），
> **一律用 tar.exe 或 7z 解压，不要用 python**。否则工具链会读到自己的密文源码。

### ★ 本机 go vet 不可用

`vet.exe -flags` 直接崩 `0xc0000005` (ACCESS_VIOLATION)，标准库源码确认是明文，所以不是加密问题——更像 DLP 驱动 hook 进程创建导致的。而 `go test` 默认会跑 vet 子集 → 所有测试 setup failed。
**对策**：`go test -vet=off ./...`，并已在 `scripts/goenv.sh` 里设 `GOFLAGS=-vet=off`（标注为**本机 workaround，不要进 CI**）。

### ★ 本机没有 C 编译器 → `-race` 用不了

`gcc` / `clang` / `cc` 全无，PortableGit 和 rustup 里也没带。`go test -race` 需要 `CGO_ENABLED=1` + mingw gcc。
**待办**：要跑竞态检测得先装 mingw-w64（winlibs，约 100MB，走代理约 8 分钟）。**目前 race 检测未验证。**

### 沙箱注意

工作区**外**的写入默认被沙箱拦在覆盖层里（表现为"命令成功但文件没变"、结果自相矛盾）。
安装 SDK、解压到 `~/.workbuddy-ai/` 这类操作**必须带 `dangerouslyDisableSandbox: true`**，否则白做。

### 修掉的 bug（ring buffer）

并行会话修了 `Write` 的环绕写法，但留了两处：
1. **超长写入分支起点错**：应从 `(total+n) % size` 开始写，而不是从 `r.pos`。两者只在 `n == size` 时巧合相等，所以大多数输入下躲过了测试。表现是 `Snapshot` 返回错位数据（`"efghijcd"` 而非 `"cdefghij"`）。
2. **`Reset()` 重置了 `pos`**：破坏「绝对序号 a → 物理下标 a % size」不变式。修法是**只清 `filled`**，`pos` 和 `total` 都不动。

不变式：`pos` 必须恒等于 `total % size`。`copyRange` 依赖它做序号→下标映射。

**核心定性**：这不是文件管理器，是 **Workspace File Transport** —— 和 PTY 传输在架构上同构（都是"把本机一个字节源搬到浏览器"），所以复用同一条 WS、同一套鉴权、同一个 Relay。

**关键决策**：
- F1 复用已有 client WS（不单开连接）；**F4 必须独立队列 + 终端帧优先**，否则下载大文件时按键延迟飙到秒级
- F2 StreamID 泛化；F3 二进制帧，绝不 Base64
- F5 流控用 **ack 窗口**（在途最多 8 块 × 64 KB），最简且天然自适应
- F7 上传写临时文件 + 原子改名；F8 默认拒绝覆盖
- **F9 Server 绝不落盘、绝不缓存整文件、不解析内容** —— 用 CI lint 守住（`internal/server` 禁止 `os.Create`/`os.OpenFile`/`os.WriteFile`）
- F10 插入为新 **Phase 8**，原 P8/P9/P10 顺延为 P9/P10/P11

**最重要的安全观点**（写进了文档，防止以后有人把校验删掉）：
> PTY 里用户敲 `cat /etc/passwd` 是**用户自己操作自己的机器**，不该拦；
> 但文件 API 是**远程界面点出来的**，没有"用户自己敲"这层语义，**必须走 allowed_workspaces 白名单**。
> 路径校验 `ResolveInRoot` **只写一次**，PTY 的 cwd 和文件 API 共用 —— 两处实现必然漂移，而漂移出来的那个就是绕过口。

**边界声明**：只做浏览/预览/下载/上传。**不做**编辑、重命名、删除、移动、权限、全盘搜索。文档里明确写了为什么这条边界必须写死 —— 开了"写"的口子之后，加"编辑"只要再加一个接口，半年后它就变成 Web IDE 了。

### ★★ 重大发现：Windows 上 Ctrl+C 对 shell 不可用（P0）

**Agent 当前的 `Signal(SignalInterrupt)` 实现（写 0x03）在 cooked mode 下是坏的。**

实测（真实 cmd.exe + ping）：

| 子进程模式 | 谁在用 | 写 0x03 的结果 |
|---|---|---|
| cooked（`PROCESSED_INPUT` 开，默认） | cmd.exe / PowerShell | ❌ 字节被 conhost 拦截 → **stdin EOF**，命令不中断 |
| raw（应用自己关掉 `PROCESSED_INPUT`） | vim / Claude Code / Codex | ✅ 0x03 作为字节送达，进程存活 |

- ConPTY 默认输入模式实测 **`0x01f7`**：`PROCESSED_INPUT|LINE_INPUT|ECHO_INPUT|MOUSE_INPUT|INSERT_MODE|QUICK_EDIT_MODE|EXTENDED_FLAGS`（**没有** `VIRTUAL_TERMINAL_INPUT`）
- **推翻了 R1 §7 的结论**：「0x03 不产生 CTRL_C_EVENT，子进程收到字符」只对 raw mode 成立
- 三条路径全试过：
  - ① 写 0x03 → 见上
  - ② `FreeConsole` + `AttachConsole(pid)` + `GenerateConsoleCtrlEvent(CTRL_C_EVENT, 0)` → **API 全返回成功但无效**。用 `GetConsoleProcessList` 确认 AttachConsole 真的生效（列表含 cmd/ping/测试进程），排除了「API 用错了」
  - ③ `conpty.dll!ConptyGenerateConsoleCtrlEvent`（Windows Terminal 用的那条）→ **本机没有 conpty.dll**，无法验证
- 影响：主用例（Claude Code 等 TUI）**不受影响**；shell 场景 Ctrl+C 不可用且破坏会话，验收标准 A8 在 shell 下不满足
- **待 JOJO 决策**：方案 A（按模式分流）+ C（UI 兜底），还是 B（随 Agent 分发 conpty.dll）

### ★ 第二个发现：子进程退出后 Read 不 EOF

Windows 上子进程退出、`Wait()` 返回后，**`Read` 仍阻塞**，要等 `Close()` 才断（Unix 相反）。
**架构文档 §6.2 第 3 点「Wait 返回 → 继续 drain 到 EOF」在 Windows 上会挂死。**
正确顺序：`Wait() → 短静默窗口 → 主动 Close() → session.exit`。

### 其他

- resize 在 Windows 是**轮询语义**（探针 150ms 轮询），不是事件 → 快速连续 resize 的中间态可能被整个跳过。Phase 6 前端防抖要注意。
- 文档 §6.4 建议 ttyprobe 放 `internal/terminal/testdata/` —— **改了**，放 `cmd/ttyprobe/`。理由：Go 工具链完全忽略 testdata，那里的代码不会被编译检查，是维护陷阱。
- Makefile 新增 `ttyprobe` / `ttyprobe-unit` / `ttyprobe-test` 三个 target。

## ★★ 亿赛通（Esafenet）规则修正 —— 读写到底该用什么

**推翻了之前「读要白名单，写要非白名单」的粗糙版本。** 本次实测：

| 操作 | 工具 | 结果 |
|---|---|---|
| 写 | **Write / Edit 工具** | **明文** ✅ |
| 写 | **bash `cat >> file` 重定向** | **密文** ❌ |
| 读 | **fcli MCP（`mcp__fcli__read`）** | **明文** ✅ ← 正解 |
| 读 | python | 明文 ✅ |
| 读 | `head` / `od` | 看文件本身：明文文件→明文，密文文件→密文 |
| 读 | Read 工具 / Grep | 明文文件→明文；密文文件→报 binary |

**实用结论**：
1. **写代码/文档一律用 Write / Edit 工具**，绝不用 bash 重定向写。
2. **读不出来的文件（报 binary / 乱码）→ 用 `mcp__fcli__read`**，正常读出明文。
3. 踩过的坑：`cat >> file <<'EOF'` 追加代码 → 文件变密文 → Read 工具再也读不了 → 只能删掉用 Write 重建。**追加代码请用 Edit。**
4. `go.mod` 长期是密文状态（Read 工具读不了），但 **Go 工具链能正常读写它**，不影响构建；要看内容用 `mcp__fcli__read` 或 `go mod edit -json`。

### ★ 测试抓出并修掉的 3 个真 bug

1. **`Conn.Close()` 死锁**：`Close` 等两个泵退出（`pumpDone.Wait`），
   而泵自己又 `defer c.Close()` → 互相等待。
   表现：连接断开后 Run 卡住，既不重连也不退出。
   **修法**：泵只 `defer c.pumpDone.Done()`；`Close` 由外部调用方负责。
2. **认证被拒被当成可重试**：`authenticate` 返回普通 error，
   而 `IsFatalClose` 只认 `*websocket.CloseError` → 无脑重连。
   **修法**：新增 `ErrAuthRejected` + `IsFatalError()`。
3. **Run 不响应 ctx 取消**：`runOnce` 结尾是裸的 `<-conn.Done()`，ctx 取消时不返回
   → 优雅退出失效。**修法**：改成 `select { ctx.Done / conn.Done }`。

**共同点**：三个都只有跑真实端到端才暴露，单元测试全绿也发现不了。
再次印证 P2 那条经验：**不 mock + 跑真链路**。

### 关键设计决策

- **attach 的 ConnID = 信封的 RequestID**（协议里 `SessionAttachPayload` 没有 conn_id 字段）。
  Server 对每个浏览器的 attach 用不同 RequestID，Agent 侧自然得到不同 view；
  detach 用同一 RequestID 就能精确摘除。**Agent 不需要理解"客户端"这个概念**。
- **Agent 侧不用 `protocol.DecodeFrom` 做方向校验**：那是给 Server 用的
  （Server 的 agent 连接上对端是 Agent），而 Agent 收到的是 Server **转发**的客户端请求。
  Agent 的等价防线是 `handleMessage` 的白名单 switch。
- **二进制帧必须校验方向**（`ValidateFrameFrom`）：否则被 XSS 拿到的浏览器
  能往 Agent 发 stdout 帧，在别人的终端里画出任意内容。
- **自定义命令的 kind 保守取 shell**：无法可靠判断任意命令行是不是 TUI，
  而猜错方向的代价不对称（把 shell 当 TUI → 用户点到会破坏会话的按钮）。

### ★★ 测试抓出的真 bug

**1. 跨端点存在性预言机（IDOR 信息泄露）**

同一台「别人的设备」：
- `GET /devices/{id}` → **404**（走 `device.Service.Get` → `device.ErrNotFound`）
- `GET /devices/{id}/sessions` → **403**（走 `authorizeDevice` → `errNoAccess`）

两个端点状态码不同 → 攻击者换一个端点就能枚举出哪些 device_id 真实存在。

**根因**：REST 层有两套「不存在/无权」的写法，各自映射到不同的状态码。
`authz.go` 的注释写着「所有不属于你的情况都返回与不存在完全相同的错误」，
但 `errNoAccess` 用的是 `CodeForbidden`（→403），而 `writeDeviceError` 手写 404。

**修法**：新增 `protocol.CodeNotFound`（→404），`errNoAccess` 与 `writeDeviceError`
统一到 **404 + `not_found` + 同一句文案**。

**固化**：`TestDeviceEndpointsAgreeOnForeignDevice` 遍历所有设备端点，
断言「别人的设备」与「不存在的设备」给出**逐字节相同**的响应。
新增端点会自动被覆盖。

**教训**：单看任何一个端点都发现不了这类问题。要测的是
**端点之间的一致性**，不是单个端点的正确性。

**2. `Store` 接口缺 `SetUserDisabled`**

`User.Disabled` 在 `authenticate` / `handleLogin` 里被读，
但**没有任何代码能写它** —— 停用账号这个功能根本不存在。

**修法**：补 `SetUserDisabled` + `ListUsers`（后者给 `user list` 用）。

**3. CLI 标志位置陷阱（可用性 bug）**

`user passwd bob@example.com -password xxx` 里 `-password` 被**静默忽略**。

**根因**：Go 的 `flag` 包遇到第一个非标志参数就停止解析。
`-password` 被当成位置参数收下，password 变量保持空值 → 转去弹交互输入 → EOF 报错。
用户看到的是「密码: 」然后报错，完全联想不到是自己把标志写在了后面。

**修法**：`parseArgs` 重排（把标志连同它需要的值挑出来，剩下才是位置参数）。
用 `Value.(interface{ IsBoolFlag() bool })` 判断布尔标志，而不是硬编码名字。

### 关键设计决策

- **路由认证按组显式挂**，不做全局 requireAuth：全局挂会逼每个 handler
  自己判断「我要不要豁免」，迟早漏一个。显式挂意味着加新路由必须主动选一次。
- **`errNoAccess` 统一到 404**：见上。
- **`pairs` 不进 Registry**：那些连接尚未认证，进注册表就可能被 Relay 当可路由目标。
- **`pending` 只有 Server 知道**：中继无状态，`request_id → client` 的映射是 Server 独有的。
- **登出吊销整族而非单令牌**：一次登录会话 = 一个 family。
- **停用账号立刻生效**：`requireAuth` 每次请求查库（§10.1 的代价与收益）。
- **`closeWithCode` 用 WriteControl 而非 send channel**：队列满时（正是慢消费者被踢的场景）
  恰恰最需要立刻发出关闭帧。
- **`classifyReadError` 恒返回 CloseNormal**：Agent 侧才认 4401/4426 为致命，
  服务端自作主张给错误码会让它把普通断线当致命错误、彻底不重连。

### ★ Windows 坑：cmd.exe 的 `/c` 被路径抢走

```
C:\Windows\System32\cmd.exe /c echo hi   → 打印 hi            ✅
C:/Windows/System32/cmd.exe /c echo hi   → 命令语法不正确。   ❌
裸 cmd /c echo hi                        → 打印 hi            ✅
```

根因：cmd.exe 用**字符串扫描**找自己的 `/c` 开关，而不是先剥掉 argv[0]。
路径里的 `/cmd.exe` 先命中 → 把 `/cmd.exe` 读成「开关 `/c` + 尾巴 `md.exe`」，
剩下的 `md.exe /c echo hi` 成了要执行的命令。而 `md` 是 cmd 的**内置命令**
（mkdir 的别名），`/c` 对它不是合法路径参数 → 报语法错误。

迷惑性在于：进程起来了、ConPTY 正常、终端里有一行中文报错，
但**那行报错和用户配置的命令毫无字面关系**。

修法：`internal/agent/normalizeCommandPath` 在 Windows 上把 `command` 的正斜杠
归一化成反斜杠。**只归一化 `command`，不碰 `args`**（args 里的 `/c` 就是开关）。
放在 `Config.Prepare()` + `ResolveCommand` 的自定义命令分支。
`e2e-terminal.sh` 里**故意**用正斜杠写 command —— 一条配置同时验证通路和归一化。
