# 文件上传延迟修复

版本：v0.1.38。附件和工作区文件页共用的 `uploadFile` 已更新，Server / Agent 协议不变。生产部署状态以发布验收回执为准，尚不能确认用户当前网络的全部瓶颈。

旧实现每块都等待“浏览器 → Server → Agent → Server → 浏览器”确认。32 KiB 初始块在确认超过 600 ms 时被不断缩小到 8 KiB，误把整个往返时间当作带宽/拥塞信号。因此高延迟链路每块都支付固定等待时间，缩块反而增加往返次数。手机若有更高延迟，会进一步放大这个问题；本次未采集用户手机网络数据。

修复采用 32 KiB 消息、最多 4 块在途的有界流水传输，按字节偏移顺序发送，在途文件内容最多 128 KiB，不把整个文件塞入连接。所有前序块确认后才发送最终发布块，保留 Agent 的临时文件、工作区限制和原子发布机制；任一错误或取消都会停止后续发送并清理该上传的临时文件。迟到回执不再驱动发送或进度。两种上传入口同时受益。

设计心理学：以接收确认更新进度，最终落盘确认前最多显示 99%，避免四舍五入导致提前显示 100%。保留原上传/取消/失败重试入口，减少传输等待且不改变授权范围。最终块已经发出后发生断线或取消，仍可能已落盘；不会自动重放上传，沿用工作区文件核对及同名保护。

验证：

- 真实上传辅助模块、虚拟 800 ms 往返确认：1 MiB + 7 字节旧版 125 次请求、100 秒、最多 1 块在途；新版 33 次请求、7.2 秒、最多 4 块在途。此为受控延迟模型，不是实际互联网测速。
- 回归覆盖字节完整性、偏移顺序、在途上限、最终块屏障、空文件与分块边界、最终确认不匹配、取消、较晚块先失败而较早回执丢失、迟到拒绝处理、进度单调及不得提前 100%。
- 隔离真实 Chrome + WebSocket，人工将每块应答延后 200 ms：桌面 1440px 上传 1 MiB + 7 字节耗时 2411 ms，390px 耗时 2437 ms；均为 33 次请求、最多 4 块在途，SHA-256 与原字节一致，上传中终端 Esc 输入仍被服务端收到。该测试未连接生产 Agent，也不代表真实手机网络和终端延迟已验收。
- `test:transfer`（含剪贴板图片回归）、类型检查和生产构建通过。

范围：仅上传，文件下载仍沿用原分块策略。真实用户网络的带宽、移动网络延迟、Cloudflare/服务器转发与 Agent 磁盘速度仍可能影响最终耗时，发布后需继续核对。
