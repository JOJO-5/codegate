# Codex 原终端自动续跑控制通道修复

## 问题与证据

2026-10-23 07:18 的线上复现中，原终端仍运行，任务首先报告控制接口连接失败；随后因用户手动输入而取消。二者是独立事件，不能把后来的关闭或输入当作此前连接失败的原因。

本机 CLI 为 0.163.0。默认控制 socket 残留，但原 daemon PID 不存在；`codex app-server daemon version` 同样返回 Windows 10061 连接拒绝。它证明故障发生在本机控制通道，并不能证明历史上 daemon 为什么退出。

原实现直接连接 `$CODEX_HOME/app-server-control/app-server-control.sock`，却未在创建终端时确保服务可用，也未明确让终端连接同一个服务。终端能交互并不证明默认共享服务承载了该对话。开启入口只检查 CLI 能力，连接失败后才反复重试，最终留下需要确认的记录。

## 修复

- 创建普通 Codex 终端前，用结构化握手验证默认控制服务；不可连接时，仅使用本机已授权 CLI 执行幂等的 `app-server daemon start`，再次握手后才启动终端。
- 新终端明确使用 `--remote unix://`，让终端与自动续跑读取同一个服务。尊重显式 `--no-daemon` 和自定义 `--remote` 配置，保留普通终端用途；这些配置的原终端续跑会被明确拒绝。
- 启动失败明确报错，不静默退回无法监测的独立进程。不 restart/stop 用户的共享 daemon。
- 新增 Server → Agent 只读 `task.check`，通过能力位 `live_continue_check` 做旧版兼容门控。Server 校验会话归属，用保存的原生身份请求检查，不接受浏览器提供的命令或工作目录。
- 开启前检查本机终端仍运行、命令与工作区授权、原生身份、线程已加载及目录相符。检查期间的新输入或会话变化会拒绝旧结果。检查不创建回执，不恢复线程，不发送模型回合。
- 未通过检查不保存续跑任务；保留输入、返回原因和恢复步骤。成功后仍由既有任务调度和回执机制执行，提交不明不重放。检查等待期间不持有任务锁，取消其他任务仍可用；并发创建在落库前再次检查 nonce 和同一对话的监测记录。
- 前端显示正在核对、禁用重复提交，并隔离切换会话后的旧响应。断线核对失败显示“尚未开启”，不误报为已启动或普通服务端异常。

## 设计心理学

把“终端运行”和“可以监测续跑”分开反馈。用户仍从“自动续跑”入口操作；等待有文字反馈，失败保留说明和重试入口，避免制造失败任务记录。沿用原布局，检查 320/390 像素窄屏及键盘焦点约束，不新增高密度信息面板。

## 验证及边界

- 先验证回归测试失败：原终端缺少显式共享服务连接，旧 Agent 未核对通道也能保存续跑任务。
- Go Agent、Server、Protocol 整包测试通过；覆盖只读检查、服务不可用与恢复、未加载线程、错误归属与目录、独立/自定义连接拒绝、并发防重，以及既有取消、断线和提交不明保护。
- 本机真实 Codex 0.163.0 的隔离测试通过：冷启动 daemon、复用原服务、经完整 Agent 创建远程终端、终端保持运行、关闭终端后共享服务仍能读取原线程。使用临时 CODEX_HOME 和本机假服务商，未使用生产凭据，模型调用为 0；隔离进程均清理。
- 本机生成的 CLI schema 包含 `ordinaryUsageAllowed` 和 `excludeResetCreditDetails`，确认现有额度协议字段仍匹配。
- 前端 UX 测试、类型检查与生产构建通过；浏览器隔离流程 15 项通过，覆盖等待/失败/恢复、输入保留、防重复、刷新恢复、键盘焦点及 320/390/1440 像素宽度。Linux amd64 Agent/Server 编译通过。
- 实际订阅耗尽 → 额度恢复 → 模型续跑尚未在生产环境验收。隔离测试和构建不等于线上已更新。

本记录描述源码验证结果，生产部署结果以本版本发布说明为准。现有独立进程里的会话无法通过启动新 daemon 无缝接管；需更新 Agent 后，在用户选择的时机结束原终端并恢复原对话。不得为完成验收而强制关闭现有会话、自动加载重复线程或重放旧任务。
