# 2026-10-25 新建与恢复会话间歇失败排查

时间均为北京时间。用户确认异常集中在 Codex 新建和恢复会话，DSH 本身正常。本次修改基于 v0.1.42，纳入 v0.1.43 发布范围；实际部署及 Agent 切换结果以发布记录为准。排查和隔离验证期间未重启正在工作的 Agent 或共享 Codex 服务。

## 现场证据

- 本机 Agent 日志在 12:14:09–12:46:41 记录了 29 次 Codex 本机控制服务不可用，涉及 `session.create` 和 `conversation.restore`。这两条路径都需要控制服务，DSH 使用其他服务链路。
- 原实现丢弃了 `codex app-server daemon start` 的全部输出，因此历史日志不能直接证明每一次失败的底层原因。
- 对同一已安装的 Codex 0.164.0 使用隔离 CODEX_HOME、相同测试程序进行对照：仓库 HEAD 的 Windows 后台启动器拒绝独立守护进程启动，Codex 明确返回后台启动器限制和 Windows 错误 5；工作区已有的启动器修正通过相同测试。测试未调用模型，未使用用户会话或凭据。
- 原启动器的 Job 只有 `KILL_ON_JOB_CLOSE`；已有修正增加 `BREAKAWAY_OK`，允许显式申请独立运行的共享服务脱离 Job，普通 Agent/终端子进程仍受生命周期管理。已有服务时能连接、服务消失后无法冷启动，能够解释短暂恢复后再次失败，但不能据此排除其他间歇问题。
- 本机当前启动器已包含此修正，运行实例开始于 12:48。12:50 后有会话 attach 成功，检查时尚未观察到新的创建/恢复失败。一次连接成功和 attach 成功都不代表完整新建、恢复流程已长期稳定。

## 本次本地补充

- Codex 启动失败按后台启动器限制、程序缺失、权限、超时、命令失败、启动后仍不可连接给出明确说明及恢复动作，保留原会话。只暂存最多 16 KiB stderr 用于固定分类，不向界面或日志返回原始输出。
- Server 的恢复中间件将 `http.ErrAbortHandler` 交回 net/http，让不完整响应真正中断。之前吞掉该信号会把截断的分块流当作正常完成，还错误记录为 handler panic。今日 15 条 `/plugins/events` 告警属于此信号，容器重启次数为 0；流中断的原始原因未确认。
- 按用户偏好，DSH 默认使用其原生布局；`CODEGATE_DSH_MOBILE_UI=true` 显式启用既有兼容层，`false` 关闭。此默认值变更尚未部署。

## 验证与设计心理学

- 先补失败测试，再实现错误分类和流中断修复；覆盖敏感输出不外泄、诊断内存上限、真实异常仍返回 500，以及真实 HTTP 代理截断流必须返回读取错误。
- Windows 隔离对照：旧启动器失败，新启动器成功；普通子进程随宿主结束，显式独立守护进程存活，无控制台窗口，退出码与 UTF-8 日志保留。仅结束测试自建进程，测试目录保留供核对。
- 真实 Codex 隔离流程通过：启动、保存历史、关闭终端、缺失历史失败、恢复原对话、重复恢复复用；模型调用为 0。该流程不使用用户历史，不代表浏览器与线上隧道已验收。
- `go test ./internal/agent -count=1 -timeout=2m`、`go test ./internal/server ./internal/config -count=1 -timeout=2m` 及对应包的 `go vet` 通过，`git diff --check` 通过。
- 反馈明确区分“启动命令结束”和“控制服务可连接”，错误提供可执行的恢复动作；保留用户会话，不盲目重放或重启共享服务。界面布局本次没有新增组件，键盘与手机真实操作尚未复核。
